# Multi-Frame Consensus & Cue Reconstruction — Milestone 5

This document answers ROADMAP.md §12's explainability requirement: what the consensus algorithm is, why it was chosen, what alternatives exist, where it fails, and what evidence supports the choice.

## What the algorithm is

`reconstruct_cues_with_consensus` (`src/glyphcue/application/consensus_reconstruction.py`) is a from-scratch Path A seam, deliberately independent of Milestone 1's Path B `reconstruct_cues` (`src/glyphcue/application/reconstruction.py`) — Path B merges complete, clean subtitle-file lines by rolling character-overlap continuation; Path A merges sparse, occasionally-noisy OCR samples of the *same* on-screen state. Reusing one algorithm for both would have forced Path B's continuation heuristic (temporal overlap + text overlap between *different* lines) onto a problem that is actually about *voting among repeated, possibly-wrong readings of one line* — a different problem, so it gets a different, purpose-built algorithm.

Five steps, in order:

0. **Aggregate same-frame regions** (`aggregate_same_frame_observations`, `src/glyphcue/application/frame_reading_aggregation.py`): one M4 OCR call can return multiple `OcrTextRegion`s for a single frame (e.g. a two-line subtitle detected as two boxes), and `build_ocr_evidence_job` creates one Observation per region — all sharing the same `frame_reference`. These are combined into one reading per frame, joined in reading order (top-to-bottom by geometry, falling back to original order when geometry is unavailable), *before* anything below ever compares two Observations — otherwise two simultaneous regions of one frame could be mistaken for two sequential time states. Every contributing region's Observation id is kept (see `member_observation_ids`), even though the combined reading gets one new id.
1. **Sort** the aggregated readings by `start_time` (source-correct PTS). The function is called with exactly one evidence run's Observations (see "Input contract" below) — never a mix of runs.
2. **Group into state runs** (`_group_into_state_runs`): walk the sorted list once. A blank-text reading (M4's confirmed-no-text marker — see "Blank-state handling" below) never joins or starts a subtitle run; it only closes whatever run precedes it. For a non-blank reading, if the *previous* M4 OCR call that produced it was itself triggered by a **detected visual change** (or was the very first OCR call in the run), it always starts a new run — real M4 evidence of a state change wins outright, regardless of how textually similar the new reading happens to be to the old one. Otherwise (the call was a **periodic confirmation** of an already-stable state, or the Observation carries no trigger evidence at all — e.g. non-OCR provenance), the reading joins the current run when `character_similarity(previous.text, next.text) >= similarity_threshold` (default `0.5`), and starts a new run otherwise. `character_similarity` is `1 - (Levenshtein distance / max(len(a), len(b)))` — a *symmetric* similarity between two peer readings, plain character-by-character comparison with no whitespace tokenization (so it behaves identically on English, Chinese, and Japanese text). It is a deliberately different formula from CER (see "Evidence hygiene" below) and is only ever the *fallback* signal, never the sole decider when M4's own trigger evidence is available.
3. **Vote within each run** (`_consensus_value`): majority vote by exact text match. Ties are broken by the tied candidate's highest-confidence observation, then by earliest occurrence — deterministic, no randomness. Every observation in the run (winning text or not, and expanded back through same-frame aggregation to every original region id) is kept in `LanguageLayer.observation_ids`, so a reviewer can see exactly what was compared, not just what won.
4. **Time the Cue from state-transition evidence, not frame math**: a Cue's `end_time` is whatever real evidence closed its run — the next kept state's first reading's `start_time`, or an intervening blank marker's `start_time`, whichever actually follows. Only a run with no such evidence at all in this evidence run (in practice, the last one) falls back to the caller-supplied `processing_end_time` (the real end of the range M4 analyzed) if given, or — as a last, honestly-documented resort — its own last reading's `end_time`, which is not a duration claim (see "Cue-ending semantics" below). This directly avoids the `timestamp = frame_index / fps` anti-pattern the codebase has guarded against since Milestone 2's PTS-correctness tests — here the guard is "don't assume duration ends at the last *sample*," the temporal analogue of "don't assume timestamps come from frame count."

## Input contract

`reconstruct_cues_for_evidence_run` (`src/glyphcue/application/evidence_run_reconstruction.py`) is the only place M5 code calls `ObservationRepository`, and it calls `list_for_run(evidence_run_id)` — never `list_all()`. This is a hard requirement, not a convenience: Observations from two different videos, or two re-runs of the same video, must never be silently merged into one reconstruction (`tests/application/test_evidence_run_reconstruction.py::test_never_aggregates_across_evidence_run_ids` proves this). `reconstruct_cues_with_consensus` itself stays a pure `list[Observation] -> (list[Cue], list[ConsensusDiagnostics])` function with no run-id parameter — the run-scoping responsibility belongs one layer up, at the fetch, matching the existing `evidence_run_id` design from Milestone 4.

## Same-frame region aggregation (frame granularity)

M4's `OcrEngine.recognize()` can legitimately return more than one `OcrTextRegion` for a single OCR call — e.g. a two-line subtitle recognized as two separate detection boxes. Before this corrective pass, `build_ocr_evidence_job` created one Observation per region, all sharing the same PTS and `frame_reference`, and M5 compared them as if they were sequential readings — two simultaneous lines of one frame could be (and, in `tests/application/test_evidence_run_to_cue_end_to_end.py::test_two_region_single_language_frame_becomes_one_cue_not_two`'s pre-fix behavior, were) treated as two different subtitle states. `aggregate_same_frame_observations` closes this: it groups by `frame_reference`, joins each group's text in reading order, and is called as literally the first step of `reconstruct_cues_with_consensus` — so every caller, including `benchmarks/multi_frame_consensus/run_evaluation.py`'s real-PaddleOCR evaluation, goes through the identical production aggregation path rather than joining region text itself.

## State-transition evidence, not just text similarity

Pairwise text similarity alone cannot distinguish "two noisy readings of the same real state" from "two different states whose text happens to look similar" (e.g. a subtitle correcting a typo, or two consecutive lines of dialogue that share several words). `ChangeTriggeredOcrPolicy` already computes, and now exposes via `last_trigger_reason`, *why* each OCR call ran: `"first_frame"`, `"change_detected"` (a real visual change crossed the threshold), or `"periodic_confirmation"` (the state was believed unchanged; this call just re-checked it). `build_ocr_evidence_job` threads this into `Observation.provenance.detail["state_trigger"]`, and M5's grouping step (`_group_into_state_runs`) checks it first: a `"change_detected"`/`"first_frame"` reading always starts a new run, and only a `"periodic_confirmation"` reading (or an Observation with no trigger evidence at all) falls back to text-similarity voting. This means a genuinely new state that happens to read very similarly to the previous one (`test_detected_change_forces_a_new_cue_even_when_text_is_very_similar`) still correctly produces two Cues, while a noisy misread from a confirmation call of an unchanged state (`test_periodic_confirmation_of_the_same_state_still_uses_similarity_voting`) still gets absorbed into one Cue by the vote. M5 trusts M4's own change-detection decision here rather than second-guessing it; if M4's detector is itself noisy (false-positive "changes"), M5 will over-split — a known dependency on M4's quality, not something M5 tries to independently correct.

## Blank-state handling and Cue-ending semantics

Two related gaps in the original M4→M5 handoff are closed here:

- **Blank states now have real evidence.** Previously, an OCR call that found no readable text was silently skipped — no Observation was ever created for it, so M5 had no way to distinguish "the subtitle really went blank here" from "no OCR call happened to run here." `build_ocr_evidence_job` now persists a single empty-text (`text=""`) marker Observation on a confirmed-blank OCR call instead. M5's grouping step treats a blank marker as real evidence that closes whatever subtitle run precedes it — ending that Cue exactly at the blank marker's `start_time` — without ever turning the blank state itself into a Cue (`test_blank_marker_ends_the_preceding_cue_without_becoming_a_cue_itself`, and the real M4→M5 regression `test_subtitle_blank_subtitle_produces_two_cues_not_three`).
- **The final Cue no longer defaults to a ~1ms instant.** `Observation.end_time = start_time + 0.001` (`_INSTANT_SPAN_SECONDS` in `ocr_evidence_job.py`) was always just a point-in-time marker, never a duration claim — but the *last* reconstructed Cue in a run (the one with no following state or blank marker to derive a real boundary from) previously fell back to exactly that 1ms span, understating real on-screen duration by orders of magnitude. `reconstruct_cues_with_consensus` and `reconstruct_cues_for_evidence_run` now accept an optional `processing_end_time` — the real end of the range M4 analyzed (e.g. `probe_media(path).duration_seconds`), which the caller who ran the M4 job already knows — and use it for the final Cue's `end_time` when supplied (`test_final_cue_uses_the_supplied_processing_end_time_not_a_1ms_instant`, and the real regression `test_final_single_observation_uses_real_processing_end_not_a_1ms_cue`). Without it, the fallback is still the honest-but-imprecise 1ms marker — documented as a known limitation of the fallback path, not silently hidden.

## Why this baseline, and not something else

ROADMAP M5 scope is explicit: *"Start with a simple explainable baseline. Do not jump directly to opaque complexity."* Majority-vote-by-exact-text is about as simple as multi-sample text consensus gets — no ML model, no learned weights, no external dependency. It is also directly explainable on a whiteboard: "count how many times each exact reading occurred; the most common one wins; ties go to whichever reading the engine was most confident about." Backstopping the grouping step with M4's own trigger evidence (rather than only ever guessing state boundaries from text similarity) is a similarly simple, already-computed, already-explainable signal — not a new model.

**Alternatives considered, not built (yet):**

- **Character-position voting** (align all readings and vote per character position, like a multiple-sequence alignment) — strictly more powerful than exact-text voting (could recover a *correct* reading that no single sample got completely right), but is meaningfully more complex to implement and explain, and alignment itself is nontrivial for CJK text where a single missing/extra character shifts every following position. Not built because the evidence below doesn't yet show exact-text voting is insufficient in the mixed-scenario case — see Evidence.
- **Confidence-weighted voting** (weight each vote by the engine's reported confidence instead of counting occurrences equally) — rejected for V1 because `OcrRuntimeInfo`/`OcrTextRegion.confidence` values are not currently validated to be well-calibrated across engines (per the Milestone 3 ADR, confidence is an engine-reported score, not something GlyphCue has independently benchmarked for calibration); using it as the *primary* signal risks trusting a wrong-but-confident reading over a right-but-modest one. It is used only as a *tie-breaker*, where its risk is smallest.
- **Timing-overlap continuation** (reuse Path B's `_continues_run` timing-overlap check) — rejected because M4's OCR calls are selective and sparse (not a dense frame stream), so consecutive Observations in the list are already temporally adjacent by construction; a timing-overlap test would add complexity without adding information Path A doesn't already have from list order.

## Failure modes (recorded, not hidden)

Two synthetic scenarios were run through the actual production algorithm and a real PaddleOCR engine (`benchmarks/multi_frame_consensus/`, results in `evaluation_results.json`) — full numbers under Evidence below. Both are constructed test scenarios; neither claims to represent how often a given degradation pattern occurs in real footage, since no real-world frequency evidence has been gathered for that.

1. **Where it helps**: when most readings of a real state agree exactly and one is an outlier (e.g. a single degraded frame among several clean confirmations), majority vote correctly discards the outlier. Evidence: in the mixed synthetic scenario, English and Chinese lines both improved from a single wrong/truncated first reading (CER 0.045 / 0.111) to an exact match (CER 0.0) once 4 clean confirmations outvoted it.
2. **Where it does not help (and can get worse)**: when *every* reading is independently degraded enough that no two are exactly equal, the vote degenerates to a many-way tie, and the algorithm falls back to the highest-confidence reading — which is not guaranteed to be the most *correct* one. In the "all 5 heavily degraded" scenario, mean consensus CER (0.219) was measurably *worse* than the single-frame baseline (0.052). The English case shows a second, related effect: severe degradation caused the OCR engine to detect the same line as more than one region in some variants, and — since none of these synthetic readings carry M4's `state_trigger` evidence (the benchmark constructs raw Observations directly, not through a real `ChangeTriggeredOcrPolicy` run) — grouping fell back entirely to text-similarity voting, which does not perfectly recombine fragmented, differently-split regions across variants; the "winning" Cue's text was assembled from out-of-order fragments (CER 0.545 for that one item).

This is the concrete, measured argument for *not* building character-position voting or confidence-weighted voting speculatively right now: the failure only shows up under near-worst-case degradation (every single sample corrupted differently, sometimes fragmenting the detected text itself), which is not what M4's `ChangeTriggeredOcrPolicy` actually produces in normal operation (it OCRs on detected change or periodic confirmation of an already-stable state, so most of a state's readings are ordinary, not independently-degraded) — and a real M4 run would additionally have real `state_trigger` evidence available to bound the grouping, which this synthetic worst-case scenario deliberately does not provide. If future evidence from real-world footage shows this failure mode is common rather than a constructed worst case, character-position voting is the documented next step — not before.

3. **The blank-state and final-Cue-boundary gaps described above are now closed** with real M4→M5 evidence (`test_subtitle_blank_subtitle_produces_two_cues_not_three`, `test_final_single_observation_uses_real_processing_end_not_a_1ms_cue`) rather than being an open, unevidenced limitation.

## Evaluation corpus

Three ground-truth lines (English, Chinese, Japanese), rendered in-script from known text via Windows system fonts (`benchmarks/multi_frame_consensus/fixture.py`) — no scraped video frame or real subtitle screenshot, matching the same copyright-safety approach as the Milestone 3/4 benchmark corpora. Each line gets 5 independently-degraded image variants (blur + contrast + additive noise + a randomly-positioned occlusion patch for the "heavy" degradation level), run through the real, pinned `PaddleOcrEngine` (`paddleocr==3.7.0`/`paddlepaddle==3.3.1`). Each variant's real OCR output is turned into one Observation *per region* — exactly what `build_ocr_evidence_job` does — and both the single-frame baseline and the consensus result are produced by calling the real `aggregate_same_frame_observations` / `reconstruct_cues_with_consensus` production functions, not by the benchmark script joining region text itself.

Two synthetic scenarios per line (constructed to probe specific behaviors, not sampled from real footage):

- **`mixed_synthetic_1_degraded_4_clean`**: 1 heavily-degraded read (placed first, modeling a bad reading right as a change is detected) + 4 mildly-blurred, otherwise clean reads (modeling settled confirmation frames).
- **`all_5_heavily_degraded`**: all 5 reads heavily degraded independently — the deliberate worst case, to honestly find where the baseline stops helping.

## Conclusion

The simple majority-vote baseline, backstopped by M4's own state-change evidence rather than text similarity alone, is the right V1 choice: it measurably helps in the mixed synthetic scenario, it is fully whiteboard-explainable, and its measured failure mode is confined to a worst-case scenario that both (a) doesn't reflect normal `ChangeTriggeredOcrPolicy` behavior and (b) is worse specifically *because* it withholds the state-trigger evidence a real M4 run would provide. Per ROADMAP's explicit instruction, added complexity (character-position voting, confidence-weighted voting) is deferred until real-world evidence — not a constructed worst case — shows it's needed.
