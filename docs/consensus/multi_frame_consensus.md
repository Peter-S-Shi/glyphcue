# Multi-Frame Consensus & Cue Reconstruction — Milestone 5

This document answers ROADMAP.md §12's explainability requirement: what the consensus algorithm is, why it was chosen, what alternatives exist, where it fails, and what evidence supports the choice.

## What the algorithm is

`reconstruct_cues_with_consensus` (`src/glyphcue/application/consensus_reconstruction.py`) is a from-scratch Path A seam, deliberately independent of Milestone 1's Path B `reconstruct_cues` (`src/glyphcue/application/reconstruction.py`) — Path B merges complete, clean subtitle-file lines by rolling character-overlap continuation; Path A merges sparse, occasionally-noisy OCR samples of the *same* on-screen state. Reusing one algorithm for both would have forced Path B's continuation heuristic (temporal overlap + text overlap between *different* lines) onto a problem that is actually about *voting among repeated, possibly-wrong readings of one line* — a different problem, so it gets a different, purpose-built algorithm.

Five steps, in order:

0. **Aggregate same-frame regions** (`aggregate_same_frame_observations`, `src/glyphcue/application/frame_reading_aggregation.py`): one M4 OCR call can return multiple `OcrTextRegion`s for a single frame (e.g. a two-line subtitle detected as two boxes), and `build_ocr_evidence_job` creates one Observation per region — all sharing the same `frame_reference`. These are combined into one reading per frame, joined in reading order (top-to-bottom by geometry, falling back to original order when geometry is unavailable), *before* anything below ever compares two Observations — otherwise two simultaneous regions of one frame could be mistaken for two sequential time states. Regions whose geometry shows genuinely non-overlapping vertical extents are joined with a real newline (`"\n"`) — real evidence of a separate visual line, e.g. an actual two-line subtitle — rather than glued together with no separator at all; without geometry for either region, there's no such evidence, so they're joined directly. Every contributing region's Observation id is kept (see `member_observation_ids`), even though the combined reading gets one new id.
1. **Sort** the aggregated readings by `start_time` (source-correct PTS). The function is called with exactly one evidence run's Observations (see "Input contract" below) — never a mix of runs.
2. **Group into state runs** (`_group_into_state_runs`): walk the sorted list once, treating both a **detected visual change** and a **blank (OCR-empty) reading** as CANDIDATE evidence, not confirmed facts — see "Candidate evidence needs confirmation" below for exactly how each is resolved. Everything that isn't a state-change candidate (a **periodic confirmation** reading, or an Observation with no trigger evidence at all — e.g. non-OCR provenance) falls back to `character_similarity(anchor.text, next.text) >= similarity_threshold` (default `0.5`), where `anchor` is the run's own first (confirmed) reading, never its most recent member — a rejected/absorbed outlier must not itself become the new comparison point for what comes after it. `character_similarity` is `1 - (Levenshtein distance / max(len(a), len(b)))` — a *symmetric* similarity between two peer readings, plain character-by-character comparison with no whitespace tokenization (so it behaves identically on English, Chinese, and Japanese text). It is a deliberately different formula from CER (see "Evidence hygiene" below).
3. **Vote within each run** (`_consensus_value` for text, `_consensus_language` for language): majority vote by exact match, but only among the run's *voting* members — blank (OCR-empty) readings and unconfirmed trailing candidates (see "Candidate evidence needs confirmation" above) never count toward the vote, no matter how many of them there are. Ties among voting members are broken by the tied candidate's highest-confidence observation, then by earliest occurrence — deterministic, no randomness. Language voting excludes observations with no reported language from the vote (falling back to `"und"` only if none report one) without ever building a separately-filtered, shorter parallel list to vote over — see "Evidence hygiene" for the crash this used to cause. Every observation in the run (voting or not, winning value or not, and expanded back through same-frame aggregation to every original region id) is still kept in `LanguageLayer.observation_ids`, so a reviewer can see exactly what was compared, not just what won or what counted.
4. **Time the Cue from state-transition evidence, not frame math**: a Cue's `end_time` is whatever real evidence closed its run — the next kept state's first reading's `start_time`, or the FIRST of a confirmed sequence of blank-marker candidates' `start_time`, whichever actually follows. Only a run with no such evidence at all in this evidence run (in practice, the last one) falls back to the caller-supplied `processing_end_time` (the real end of the range M4 analyzed) if given, or — as a last, honestly-documented resort — its own last reading's `end_time`, which is not a duration claim (see "Cue-ending semantics" below). This directly avoids the `timestamp = frame_index / fps` anti-pattern the codebase has guarded against since Milestone 2's PTS-correctness tests — here the guard is "don't assume duration ends at the last *sample*," the temporal analogue of "don't assume timestamps come from frame count."

## Candidate evidence needs confirmation

Two corrective passes to this milestone found that M5's two "hard evidence" signals were being trusted too literally — including, in the second pass, when there was no later evidence available at all to judge a candidate by:

- **`state_trigger == "change_detected"` is only a candidate boundary from M4's cheap pixel-difference detector**, not proof the subtitle itself changed — a moving or flickering background behind static burned-in text, or a compression artifact, can cross the change threshold without the subtitle text changing at all. If the OCR reading that comes with a `"change_detected"`/`"first_frame"` trigger is textually unchanged from the run's anchor text, no candidate/confirmation step is even needed: nothing is being proposed to change, so it's absorbed immediately (`test_change_detected_with_an_unchanged_reading_does_not_split`). If the reading genuinely differs, it becomes a candidate resolved by `_confirmed_by_next_evidence` against the *next* real (non-blank) reading, three ways:
  - **Confirmed** — the next reading keeps supporting the candidate's text: it starts a real new run (`test_change_detected_candidate_confirmed_when_next_evidence_supports_it`). A real A→B transition, including when B looks very similar to A, is still confirmed correctly this way.
  - **Rejected by real evidence** — the next reading reverts to the run's original text: the candidate is a false positive, absorbed into the current run as an outlier, and still counts toward that run's text/language vote for provenance and disagreement stats (`test_change_detected_candidate_rejected_when_next_evidence_reverts`).
  - **Unconfirmed (trailing)** — there is no next real reading at all (the candidate is the last reading in the evidence run): with nothing to confirm *or* refute it, it is absorbed into the current run for provenance but is **excluded from that run's text/language vote**, so it cannot silently override the already-established reading just because it happens to carry a higher OCR confidence score (`test_unconfirmed_trailing_change_candidate_does_not_override_the_established_text`). It also never opens a new Cue on its own.
- **A single OCR-empty (blank) reading is only a candidate for "the subtitle went blank," not confirmed.** M4's OCR-empty marker is held as a pending candidate (along with any further consecutive blank readings) until the next non-blank reading arrives. If that reading matches the run's anchor text, the blank span was a transient OCR-empty glitch — it's rejected, and the held blank observations are still kept in the run for provenance but are never counted toward the run's text/language vote, no matter how many of them there are (`test_a_single_ocr_empty_read_does_not_end_a_cue`, `test_blank_evidence_never_wins_the_text_vote_by_sheer_count`). If it doesn't match, the gap is confirmed real, and the boundary backdates to the FIRST blank candidate's `start_time`, not the last (`test_sustained_blank_evidence_confirms_a_real_gap_backdated_to_the_first_candidate`) — that is genuinely when the state started going blank. A **trailing** run of blank candidates (nothing after them at all) needs at least 2 consecutive blank reads to be confirmed as a real gap — a single trailing blank has nothing to confirm or refute it, so on its own it must not truncate the Cue (`test_a_single_trailing_blank_candidate_does_not_truncate_the_cue`, `test_two_consecutive_trailing_blanks_confirm_a_real_gap`).

All three mechanisms share the same underlying principle: a cheap, real-time detector (visual diff, or "OCR found nothing this call") is *evidence worth acting on*, but not *proof* on its own — and, critically, the *absence* of later evidence is not proof either. A trailing candidate with nothing after it to check against is genuinely unresolved, not "confirmed by default": it stays in the run for a reviewer to see, but it never gets to unilaterally end a Cue or decide what that Cue's text/language is.

## Input contract

`reconstruct_cues_for_evidence_run` (`src/glyphcue/application/evidence_run_reconstruction.py`) is the only place M5 code calls `ObservationRepository`, and it calls `list_for_run(evidence_run_id)` — never `list_all()`. This is a hard requirement, not a convenience: Observations from two different videos, or two re-runs of the same video, must never be silently merged into one reconstruction (`tests/application/test_evidence_run_reconstruction.py::test_never_aggregates_across_evidence_run_ids` proves this). `reconstruct_cues_with_consensus` itself stays a pure `list[Observation] -> (list[Cue], list[ConsensusDiagnostics])` function with no run-id parameter — the run-scoping responsibility belongs one layer up, at the fetch, matching the existing `evidence_run_id` design from Milestone 4.

## Same-frame region aggregation (frame granularity)

M4's `OcrEngine.recognize()` can legitimately return more than one `OcrTextRegion` for a single OCR call — e.g. a two-line subtitle recognized as two separate detection boxes. Before this corrective pass, `build_ocr_evidence_job` created one Observation per region, all sharing the same PTS and `frame_reference`, and M5 compared them as if they were sequential readings — two simultaneous lines of one frame could be (and, in `tests/application/test_evidence_run_to_cue_end_to_end.py::test_two_region_single_language_frame_becomes_one_cue_not_two`'s pre-fix behavior, were) treated as two different subtitle states. `aggregate_same_frame_observations` closes this: it groups by `frame_reference`, joins each group's text in reading order, and is called as literally the first step of `reconstruct_cues_with_consensus` — so every caller, including `benchmarks/multi_frame_consensus/run_evaluation.py`'s real-PaddleOCR evaluation, goes through the identical production aggregation path rather than joining region text itself.

`ChangeTriggeredOcrPolicy` already computes, and now exposes via `last_trigger_reason`, *why* each OCR call ran: `"first_frame"`, `"change_detected"` (a pixel-diff detector's threshold was crossed), or `"periodic_confirmation"` (the state was believed unchanged; this call just re-checked it). `build_ocr_evidence_job` threads this into `Observation.provenance.detail["state_trigger"]`, and M5's grouping step (`_group_into_state_runs`) uses it as candidate evidence for a state-change boundary — see "Candidate evidence needs confirmation" above for exactly how it's confirmed or rejected, rather than trusted outright. M5 trusts M4's own change-detection decision as candidate evidence, not a second-guessed one; if M4's detector is itself noisy (frequent false-positive "changes"), the confirmation mechanism absorbs the false positives rather than M5 independently re-deriving change detection from scratch.

## Blank-state handling and Cue-ending semantics

Two related gaps in the original M4→M5 handoff are closed here:

- **Blank states now have real evidence.** Previously, an OCR call that found no readable text was silently skipped — no Observation was ever created for it, so M5 had no way to distinguish "the subtitle really went blank here" from "no OCR call happened to run here." `build_ocr_evidence_job` now persists a single empty-text (`text=""`) marker Observation on an OCR-empty call instead — candidate evidence for M5 to resolve, not a confirmed fact on its own. As described in "Candidate evidence needs confirmation" above, M5 treats this as a candidate, not an immediate boundary: a single blank reading that's followed by a reading matching the run's original text is rejected as an OCR-empty glitch and the run continues (and is excluded from that run's text/language vote regardless of how many blank reads there were); a blank span that isn't contradicted by the next real reading, or that sustains for at least 2 consecutive reads with nothing after it at all, is confirmed, and the preceding Cue ends at the FIRST blank candidate's `start_time` — never at a later one, and the blank state itself never becomes a Cue (`test_blank_marker_ends_the_preceding_cue_without_becoming_a_cue_itself`, `test_a_single_ocr_empty_read_does_not_end_a_cue`, `test_sustained_blank_evidence_confirms_a_real_gap_backdated_to_the_first_candidate`, `test_a_single_trailing_blank_candidate_does_not_truncate_the_cue`, `test_two_consecutive_trailing_blanks_confirm_a_real_gap`, `test_blank_evidence_never_wins_the_text_vote_by_sheer_count`, and the real M4→M5 regression `test_subtitle_blank_subtitle_produces_two_cues_not_three`).
- **The final Cue no longer defaults to a ~1ms instant.** `Observation.end_time = start_time + 0.001` (`_INSTANT_SPAN_SECONDS` in `ocr_evidence_job.py`) was always just a point-in-time marker, never a duration claim — but the *last* reconstructed Cue in a run (the one with no following state or blank marker to derive a real boundary from) previously fell back to exactly that 1ms span, understating real on-screen duration by orders of magnitude. `reconstruct_cues_with_consensus` and `reconstruct_cues_for_evidence_run` now accept an optional `processing_end_time` — the real end of the range M4 analyzed (e.g. `probe_media(path).duration_seconds`), which the caller who ran the M4 job already knows — and use it for the final Cue's `end_time` when supplied (`test_final_cue_uses_the_supplied_processing_end_time_not_a_1ms_instant`, and the real regression `test_final_single_observation_uses_real_processing_end_not_a_1ms_cue`). Without it, the fallback is still the honest-but-imprecise 1ms marker — documented as a known limitation of the fallback path, not silently hidden.

## Why this baseline, and not something else

ROADMAP M5 scope is explicit: *"Start with a simple explainable baseline. Do not jump directly to opaque complexity."* Majority-vote-by-exact-text is about as simple as multi-sample text consensus gets — no ML model, no learned weights, no external dependency. It is also directly explainable on a whiteboard: "count how many times each exact reading occurred; the most common one wins; ties go to whichever reading the engine was most confident about." Backstopping the grouping step with M4's own trigger evidence (rather than only ever guessing state boundaries from text similarity) is a similarly simple, already-computed, already-explainable signal — not a new model.

**Alternatives considered, not built (yet):**

- **Character-position voting** (align all readings and vote per character position, like a multiple-sequence alignment) — strictly more powerful than exact-text voting (could recover a *correct* reading that no single sample got completely right), but is meaningfully more complex to implement and explain, and alignment itself is nontrivial for CJK text where a single missing/extra character shifts every following position. Not built because the evidence below doesn't yet show exact-text voting is insufficient in the mixed-scenario case — see Evidence.
- **Confidence-weighted voting** (weight each vote by the engine's reported confidence instead of counting occurrences equally) — rejected for V1 because `OcrRuntimeInfo`/`OcrTextRegion.confidence` values are not currently validated to be well-calibrated across engines (per the Milestone 3 ADR, confidence is an engine-reported score, not something GlyphCue has independently benchmarked for calibration); using it as the *primary* signal risks trusting a wrong-but-confident reading over a right-but-modest one. It is used only as a *tie-breaker*, where its risk is smallest.
- **Timing-overlap continuation** (reuse Path B's `_continues_run` timing-overlap check) — rejected because M4's OCR calls are selective and sparse (not a dense frame stream), so consecutive Observations in the list are already temporally adjacent by construction; a timing-overlap test would add complexity without adding information Path A doesn't already have from list order.

## Failure modes (recorded, not hidden)

Two synthetic scenarios were run through the actual production algorithm and a real PaddleOCR engine (`benchmarks/multi_frame_consensus/`, results in `evaluation_results.json`) — full numbers under Evidence below. Both are constructed test scenarios; neither claims to represent how often a given degradation pattern occurs in real footage, since no real-world frequency evidence has been gathered for that.

1. **Where it helps**: when most readings of a real state agree exactly and one is an outlier (e.g. a single degraded frame among several clean confirmations), majority vote correctly discards the outlier. Evidence: in the mixed synthetic scenario, English and Chinese lines both improved from a single wrong/truncated first reading (CER 0.045 / 0.111) to an exact match (CER 0.0) once 4 clean confirmations outvoted it.
2. **Where it does not help (and can get worse)**: when *every* reading is independently degraded enough that no two are exactly equal, the vote degenerates to a many-way tie. In the "all 5 heavily degraded" scenario, mean consensus CER (0.105) was still measurably *worse* than the single-frame baseline (0.052), driven by the English item: severe degradation caused the OCR engine to detect the same line as more than one region in some variants, and — since none of these synthetic readings carry M4's `state_trigger` evidence (the benchmark constructs raw Observations directly, not through a real `ChangeTriggeredOcrPolicy` run — see "Evaluation corpus" below) — grouping falls back entirely to text-similarity voting, which produced 4 separate runs (`cue_count: 4`) instead of one for that item, and the "winning" run's text (CER 0.2045) came from partial, fragmented regions.

This is the concrete, measured argument for *not* building character-position voting or confidence-weighted voting speculatively right now: the failure only shows up under near-worst-case degradation (every single sample corrupted differently, sometimes fragmenting the detected text itself) combined with the *absence* of `state_trigger` evidence — which is not what M4's `ChangeTriggeredOcrPolicy` actually produces in normal operation (it OCRs on detected change or periodic confirmation of an already-stable state, so most of a state's readings are ordinary, not independently-degraded, and every reading carries real trigger evidence). If future evidence from real-world footage shows this failure mode is common rather than a constructed worst case, character-position voting is the documented next step — not before.

3. **The blank-state and final-Cue-boundary gaps described above are now closed** with real M4→M5 evidence (`test_subtitle_blank_subtitle_produces_two_cues_not_three`, `test_final_single_observation_uses_real_processing_end_not_a_1ms_cue`) rather than being an open, unevidenced limitation.

## Evaluation corpus

Three ground-truth lines (English, Chinese, Japanese), rendered in-script from known text via Windows system fonts (`benchmarks/multi_frame_consensus/fixture.py`) — no scraped video frame or real subtitle screenshot, matching the same copyright-safety approach as the Milestone 3/4 benchmark corpora. Each line gets 5 independently-degraded image variants (blur + contrast + additive noise + a randomly-positioned occlusion patch for the "heavy" degradation level), run through the real, pinned `PaddleOcrEngine` (`paddleocr==3.7.0`/`paddlepaddle==3.3.1`). Each variant's real OCR output is turned into one Observation *per region* — exactly what `build_ocr_evidence_job` does — and both the single-frame baseline and the consensus result are produced by calling the real `aggregate_same_frame_observations` / `reconstruct_cues_with_consensus` production functions, not by the benchmark script joining region text itself.

**Scope, stated precisely**: this benchmark exercises real OCR output through the real production aggregation and consensus functions. It does **not** exercise real M4 invocation-policy/trigger semantics — the Observations it builds have no `state_trigger` provenance and never go through a real `ChangeTriggeredOcrPolicy` decision or `build_ocr_evidence_job` run, so it cannot demonstrate the "candidate evidence needs confirmation" mechanism at all (see above). That mechanism is verified separately — with a real `ChangeTriggeredOcrPolicy`, real `state_trigger` stamping, and synthetic (not real-OCR) pixel content — by the real M4→M5 integration test `tests/application/test_evidence_run_to_cue_end_to_end.py::test_visual_false_positive_change_detection_does_not_over_split`, which proves an oscillating background that repeatedly fires real `"change_detected"` triggers does not over-split a subtitle whose OCR reading never actually changes.

Two synthetic scenarios per line (constructed to probe specific behaviors, not sampled from real footage):

- **`mixed_synthetic_1_degraded_4_clean`**: 1 heavily-degraded read (placed first, modeling a bad reading right as a change is detected) + 4 mildly-blurred, otherwise clean reads (modeling settled confirmation frames).
- **`all_5_heavily_degraded`**: all 5 reads heavily degraded independently — the deliberate worst case, to honestly find where the baseline stops helping.

## Evidence hygiene

A corrective pass to this milestone found and fixed a real crash: the language-consensus tie-break used to vote over a `languages` list that had already been filtered to drop `None`-language observations, while its tie-break lookup indexed by `enumerate(run)` (the *unfiltered* length) — an `IndexError` as soon as a tie occurred with any `None`-language observation present in the run. `_consensus_language` now reads `observation.language` straight off `run` by index, never building a separately-filtered parallel list, making that class of misalignment structurally impossible (`test_language_tie_break_does_not_crash_when_some_observations_have_no_language`).

## Conclusion

The simple majority-vote baseline, backstopped by M4's own state-change evidence rather than text similarity alone, is the right V1 choice: it measurably helps in the mixed synthetic scenario, it is fully whiteboard-explainable, and its measured failure mode is confined to a worst-case scenario that both (a) doesn't reflect normal `ChangeTriggeredOcrPolicy` behavior and (b) is worse specifically *because* it withholds the state-trigger evidence a real M4 run would provide. Per ROADMAP's explicit instruction, added complexity (character-position voting, confidence-weighted voting) is deferred until real-world evidence — not a constructed worst case — shows it's needed.
